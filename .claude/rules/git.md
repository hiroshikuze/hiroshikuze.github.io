# rules/git.md — Git Workflow

すべてYes/Noで判定できる条件として記述。Noの場合は修正してから進む。

---

## ブランチ

- [ ] 作業ブランチは `claude/<slug>` 形式か？
- [ ] `main` または `master` への直接プッシュではないか？（ユーザーの明示的な許可がある場合を除く）
- [ ] PR作成はユーザーから明示的に依頼されたか？（依頼なしでは作成しない）
- [ ] 操作対象は `hiroshikuze/hiroshikuze.github.io`のみか？

## コミット

- [ ] コミットメッセージは日本語の命令形
- [ ] 1コミットに含まれる変更は1つの論理的な変更のみか？
- [ ] 公開済みコミットを `--amend` していないか？（修正は新規コミットで行う）
- [ ] `.env` やAPIキーなどの秘密情報をコミットしていないか？

## プッシュ

- [ ] `git push -u origin <branch-name>` の形式を使っているか？
- [ ] `--force` オプションをユーザーの明示的な指示なしに使っていないか？
- [ ] ネットワークエラー時は指数バックオフ（2 s → 4 s → 8 s → 16 s）でリトライしているか？

## プルリクエスト

- [ ] **PR作成前に`git fetch origin main`で最新化したうえでコンフリクト確認をしたか？**確認手順：①`git fetch origin main`で最新化、②`git merge-tree --write-tree origin/main HEAD`でドライラン（**終了コードが0ならコンフリクトなし、1ならあり**。出力に`CONFLICT`が出る。③コンフリクトが出たら実際に`git merge origin/main`してその場で解消してからPRを作成する（コンフリクトを抱えたままPRだけ作らない。`git merge`は単独のコマンドで実行して衝突の有無を確かめてから`add`・`commit`・`push`に進む。つないで実行しない）。④**同じ作業で複数のPRを同時に出す場合は、PR同士のコンフリクトも確認する**（`git merge-tree --write-tree origin/<branchA> origin/<branchB>`）。`docs/decision-log.md`のような追記式のファイルは、全PRが同じ末尾に追記するため、先にマージされたPRと必ず衝突する。後から出すPRに、先のブランチを取り込んで解消しておけば、マージの順序を問わない。PR作成後にGitHubが`mergeable_state: dirty`と返した場合も同様に即座に解消する（`mergeable_state`は`unknown`→確定まで数秒かかることがあるため、作成直後は一呼吸置いて再取得する）。プッシュ前と入力時のフックが、同じ確認を機械的におこなう（下の「機械的な強制」参照）
- [ ] PRのタイトル・本文（Summary・Test plan含む）は日本語で書いているか？
- [ ] `rules/writing.md`（JTF・ひらく漢字等）に沿っているか？
- [ ] GitHub Issue由来の依頼か？→ Yesならその対応PRの本文に`Closes #<issue番号>`を含めたか？
- [ ] **PRの`main`ブランチへのマージはユーザーが自分で行うか？**

## 機械的な強制

PR作成前後の競合確認と、マージ済みPRへの追加pushは、実行者の注意だけに頼ると見落とす。そのため、`.claude/settings.json`のフックで機械的に確認する。

| フック | 動くタイミング | 動作 |
| --- | --- | --- |
| プッシュ前（`PreToolUse`・`Bash`） | `git push`を含むコマンドの直前 | 次のどちらかに該当したら**ブロック**する（終了コード2）。①前回プッシュ分が`main`に取り込み済み。②`origin/main`と競合する |
| 入力時（`UserPromptSubmit`） | ユーザーが発言するたび | 同じ確認をして、問題があるときだけ一言を出す。**ブロックしない**。`git fetch`は60秒に1回に間引く |
